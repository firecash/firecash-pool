===============================================================================
 ZKas ($zkas) — Pool Integration Guide
===============================================================================

Who this is for: anyone running mining-pool software (Miningcore, katpool,
kaspa-stratum-bridge, a custom Go/Rust/Node bridge, or your own stack) who
wants to mine ZKas. It assumes you will NOT use our pool code — it tells you
exactly which behaviours ZKas requires and points at the exact file, symbol and
constant in the node that defines each one, so you can implement them yourself.

Node source of truth. Every file path in this guide is relative to the root
of that repository, not this one:

    https://github.com/firecash/zkas-rusty

Read section 1 first. It is the entire integration in one page; everything
after it is detail.


-------------------------------------------------------------------------------
 0. COIN AND NETWORK AT A GLANCE
-------------------------------------------------------------------------------

  Name / ticker        ZKas / $zkas
  Base unit            1 $zkas = 100,000,000 sompi (1e8)
  Chain type           rusty-kaspa fork (kaspad v2.0.1 lineage), GHOSTDAG BlockDAG
  Privacy              shielded-by-default; value lives in an Orchard (Halo 2)
                       shielded pool. The coinbase reward is minted directly as
                       a shielded note. Mining is unaffected — you still hash
                       plain block headers.
  Proof of Work        kHeavyHash, BYTE-IDENTICAL to Kaspa mainnet
  Block rate           1 BPS (target_time_per_block = 1000 ms)
  Merged mining        yes, with Kaspa (AuxPoW). Active from genesis on the
                       live network. Optional — native mining always works.
  Address format       bech32, HRP "zkas:" (testnet "zkastest:",
                       devnet "zkasdev:", simnet "zkassim:")
  Network id           zkas-mainnet   (wire + datadir identity)
  Default node ports   gRPC 16810, P2P 16811   (Kaspa's are 16110/16111, so a
                       ZKas node and a Kaspa node co-exist with no clash)
  Coinbase maturity    100 blocks (100 s at 1 BPS)
                       consensus/core/src/config/constants.rs
                       — COINBASE_MATURITY_SECONDS = 100
  Shielded spendable   600 blocks (~10 min) — a shielded note can only be spent
                       once its anchor has matured
                       consensus/core/src/config/params.rs — shielded_anchor_depth

 EMISSION

  Initial subsidy      60 $zkas per block at 1 BPS (6,000,000,000 sompi)
  Halving              every 3 months
                       consensus/src/processes/coinbase.rs
                       — SUBSIDY_HALVING_INTERVAL_MONTHS = 3
  Dev fee              5%, CONSENSUS-ENFORCED, appended as one extra coinbase
                       output. The finding miner receives 57 $zkas of the
                       initial 60. Value is conserved: the fee is skimmed from
                       the subsidy, never from transaction fees.
                       consensus/src/processes/coinbase.rs
                       — dev_fee_permille / dev_fee_cut / expected_coinbase_transaction
  Perpetual tail       the emission curve decays below a floor around month 10,
                       after which a fixed tail is paid forever:
                         6 $zkas/s   until real month 24
                         0.6 $zkas/s from month 24 onward  (~18.9M $zkas/year)
                       consensus/src/processes/coinbase.rs
                       — TAIL_SUBSIDY_INITIAL_PER_SEC_SOMPI / _FINAL_ / TAIL_STEP_DOWN_MONTH

 SUPPLY

  ZKas has NO fixed maximum supply. The tail emission is perpetual by design —
  it funds miner security forever instead of relying on fee revenue alone.
  What IS bounded is the deflationary curve: it issues ~703M $zkas in total and
  then contributes nothing.

  Computed from the live schedule (1 BPS, curve + tail, dev fee included since
  the fee is part of the subsidy, not additional to it):

      after 3 months        ~351M $zkas
      after 6 months        ~527M
      after 1 year          ~665M
      after 2 years         ~854M
      after 3 years         ~873M
      after 5 years         ~911M
      after 10 years       ~1.005B
      after 20 years       ~1.195B
      after 100 years      ~2.71B

  Long-run inflation is therefore ~2.2% at tail onset (~year 2), decaying
  toward ~1% and below over decades as the base grows. Emission is heavily
  front-loaded: roughly half of all curve issuance happens in the first quarter.

 SHIELDED TRANSACTION LIMITS (matters for payout batching, not for mining)

  Max spends per tx     38     sdk/wallet-engine/src/payment.rs — max_spends_per_tx()
  Max actions per tx    38     sdk/wallet-engine/src/payment.rs — max_actions_per_tx()
  Max payees per tx     37     sdk/wallet-engine/src/payment.rs — max_payees_per_tx()

  "38" counts NOTES, not coins. A wallet holding 47,000 coinbase notes of 57
  $zkas each needs ceil(47000/38) transactions to spend them all, regardless of
  the amount. Proving cost is ~2.4 core-seconds PER NOTE SPENT, so a note-heavy
  treasury is slow to pay out until it is consolidated. See docs/WALLETD.md in
  the node repo for the pool/exchange playbook.

 1. THE WHOLE INTEGRATION, IN ONE PAGE
-------------------------------------------------------------------------------

Because the PoW is byte-identical to Kaspa, your stratum layer, share
validation, vardiff, job distribution and difficulty maths need NO changes. An
unmodified Kaspa ASIC hashes ZKas headers correctly with zero configuration.

Exactly five things differ. Only the first three are mandatory.

  (1) The payout address is a SHIELDED address, version 9, not a P2PK address.
      You pass a "zkas:" address to getBlockTemplate exactly like a "kaspa:"
      one, but the resulting coinbase output script is a raw 43-byte Orchard
      address, which is NOT a standard script class. If your pool validates
      that a coinbase output "looks like P2PK/P2SH" before accepting a
      template, that check will reject every ZKas template. Remove it.
        crypto/addresses/src/lib.rs      — Version::ShieldedOrchard = 9
        crypto/txscript/src/standard.rs  — pay_to_address_script -> pay_to_shielded_address
        crypto/txscript/src/script_class.rs — ShieldedOrchard => ScriptClass::NonStandard

  (2) The coinbase carries a mandatory 5% dev-fee output. Submit the node's
      template coinbase VERBATIM. If you rebuild or rewrite the coinbase, you
      must reproduce the node's expected transaction byte for byte, dev-fee
      output included, or the block is rejected.
        consensus/src/processes/coinbase.rs — expected_coinbase_transaction()

  (3) The coinbase PAYLOAD has an extra 32-byte field. ZKas inserts the
      shielded state root between `subsidy` and the script-pubkey block:

          Kaspa:  blue_score(8) | subsidy(8) |               spk_version(2) | spk_len(1) | spk | extra_data
          ZKas:   blue_score(8) | subsidy(8) | shielded_root(32) | spk_version(2) | spk_len(1) | spk | extra_data

      Any pool that writes its extranonce into the coinbase payload at a
      HARDCODED OFFSET will corrupt the payload on ZKas. Shift by 32 bytes, or
      better, parse the payload rather than index into it.
        consensus/src/processes/coinbase.rs
        — serialize_coinbase_payload / modify_coinbase_payload / deserialize_coinbase_payload
        — LENGTH_OF_SHIELDED_COMMITMENT = 32, MIN_PAYLOAD_LENGTH

  (4) OPTIONAL — merged mining with Kaspa (AuxPoW). One hash earns both KAS and
      $zkas. Native mining always remains valid; you never have to do this.
      Section 4.

  (5) OPTIONAL — custodial payouts. If you mine to your own treasury rather
      than direct-to-miner, you need shielded payout tooling because there are
      no transparent UTXOs to sweep. Section 6.

If you do (1), (2) and (3), you are mining ZKas.


-------------------------------------------------------------------------------
 2. STANDING UP NATIVE MINING (works today with any Kaspa-style pool)
-------------------------------------------------------------------------------

  1. Run a ZKas node:

       kaspad --appdir=<dir> --rpclisten=127.0.0.1:16110 --utxoindex

     Add --enable-unsynced-mining ONLY when bootstrapping a brand-new network
     with no peers. Never on a pool that mines the live chain.

     (16810 is the ZKas default; the reference pool overrides it to 16110 so
     existing Kaspa tooling with hardcoded ports works unchanged. Pick either,
     be consistent.)

  2. Point your bridge at that node's gRPC. getBlockTemplate / submitBlock
     behave exactly as on Kaspa:

       GetBlockTemplateRequest { pay_address: "zkas:...", extra_data: <your extranonce> }

     The node rejects a pay_address whose HRP does not match its own network —
     "invalid prefix ..." means you pointed a zkas: address at a Kaspa node, or
     a pre-rebrand node at a zkas: address.
       rpc/service/src/service.rs — get_block_template_call, prefix check

  3. Hand the header to miners over stratum unchanged. kHeavyHash ASICs
     (Bitmain, IceRiver, Goldshell, GodMiner firmware, …) work as-is.

  4. Submit solved blocks with submitBlock. Native blocks need no aux data.

  5. Pay miners to "zkas:" addresses. The simplest correct pool is a DIRECT
     pool: no coinbase override, so the block template pays the coinbase
     straight to the address the finding miner authorized with, and the chain
     mints the reward as a shielded note to that miner. The pool never holds
     funds and there is nothing to sweep, claim or sign.


-------------------------------------------------------------------------------
 3. TEMPLATE CACHING: THE ONE BUG THAT COSTS YOU BLOCKS
-------------------------------------------------------------------------------

This is worth its own section because it silently destroyed ~80% of blocks on
the reference pool before it was found.

Kaspa pools commonly cache one block template and rewrite the miner's payout
into it per worker, instead of calling getBlockTemplate again. The usual
shortcut is "rewrite the LAST coinbase output". On ZKas the last coinbase
output is the DEV-FEE output, and the second-to-last may be the red-block
reward. Rewriting `outputs.last()` therefore hijacks the dev fee, leaves the
red reward stale, and every such block is rejected with:

    "coinbase transaction is not built as expected"

The node's own template-modify path shows the correct shape: keep blue score,
subsidy and the shielded commitment; only re-point the miner's own output(s).

    mining/src/block_template/builder.rs        — modify_block_template()
    consensus/src/processes/coinbase.rs         — modify_coinbase_payload()

If your pool caches templates, either:
  - re-point by scanning the outputs in REVERSE and skipping the dev-fee output
    (it pays the dev recipient, a version-0 script whose first 43 bytes are the
    dev fund's Orchard address), or
  - simplest and always correct: call getBlockTemplate per miner and cache
    nothing.

Watch your node log for "coinbase transaction is not built as expected". A
non-zero rate of that message means you are losing blocks, not that miners are
sending bad shares.


-------------------------------------------------------------------------------
 4. MERGED MINING (AUXPOW) — OPTIONAL
-------------------------------------------------------------------------------

A ZKas block is valid if EITHER holds:

  (A) NATIVE. The block's own kHeavyHash header clears the block's ZKas target.
      Ordinary mining, identical to Kaspa. This is the backbone: chain liveness
      never depends on Kaspa miners. Accepted at all times.

  (B) AUXPOW. The block carries a proof that a PARENT kHeavyHash block
      (typically a real Kaspa block) did work clearing *ZKas's own* target and
      is cryptographically bound to this ZKas block.

The aux proof is checked against ZKAS'S target from its own DAA retarget, not
Kaspa's. Kaspa's target is far harder, so hashes that fail Kaspa routinely
clear ZKas — merged mining adds ZKas security at essentially zero marginal cost
to a Kaspa miner.

The verifier tries NATIVE first, then aux. A valid native block can never be
invalidated by a malformed or stripped aux proof, because aux data is excluded
from the block hash.

 4.1 BINDING CHAIN

    pow(parent_header) -> parent_header.hash_merkle_root -> parent_coinbase -> H_zk

  where H_zk is the ZKas block hash.

  1. Build the ZKas block and compute H_zk. H_zk is computed over the explicit
     header fields and EXCLUDES aux_pow, so it is stable no matter which parent
     later carries it.
       consensus/core/src/hashing/header.rs — hash() (no aux_pow term)

     CRITICAL: H_zk commits the ZKas coinbase through hash_merkle_root, and the
     coinbase carries the mandatory dev-fee output. Use the template coinbase
     verbatim. If you rebuild it, the H_zk you commit into the parent will not
     equal the hash of the block the node validates, the binding check fails,
     and — since a merged block has no native PoW to fall back on — submitBlock
     returns "block has invalid proof-of-work". This is the single most common
     cause of a rejected merged block.

  2. Embed the commitment in the PARENT block's coinbase payload, in the
     miner-writable extra_data slot — the only field you can set in a real
     Kaspa block without modifying Kaspa. Exactly once:

         MERGE_MINE_MAGIC (4 bytes, ASCII "ZKMM") || H_zk (32 bytes)

     Duplicate or ambiguous commitments are rejected, erring safe.
       consensus/core/src/auxpow.rs — MERGE_MINE_MAGIC, embed_commitment(),
                                      committed_hash()

  3. Mine the parent header with kHeavyHash against ZKAS's bits.

  4. Submit the ZKas block with the aux proof attached:

         AuxPow {
             parent_header:          Header,        // the mined parent
             parent_coinbase:        Transaction,   // carries ZKMM || H_zk
             coinbase_merkle_branch: Vec<Hash>,     // coinbase (leaf 0) -> root
         }

       consensus/core/src/auxpow.rs — struct AuxPow, MAX_COINBASE_MERKLE_BRANCH = 64

 4.2 WHAT THE VERIFIER CHECKS

    a. committed_hash(parent_coinbase) == H_zk                       (binding)
    b. fold(coinbase, branch) == parent_header.hash_merkle_root      (inclusion)
    c. kHeavyHash(parent_header, parent.nonce) <= ZKas target        (work)

       consensus/pow/src/auxpow.rs
       — verify_aux_pow()     the three checks above
       — check_pow_dual()     native-then-aux acceptance
       — check_pow_gated()    the same, behind the activation gate

  The parent need NOT be a valid Kaspa block — only that real kHeavyHash work,
  bound to H_zk, cleared ZKas's target. Stealing another block's PoW fails: a
  parent committing to H_a cannot be reused for H_b.

 4.3 ACTIVATION

  Aux acceptance sits behind a ForkActivation keyed on DAA score. On the LIVE
  network merged mining is active FROM GENESIS (merged_mining_activation =
  always), so both solution types are accepted today. A future relaunch may
  gate it to a DAA score, in which case only native solutions are accepted
  before that score. Native is never turned off — there is no flag day for
  miners. The gate reads the block's own DAA score, which consensus re-derives,
  so a block cannot lie about its score to unlock aux early.

 4.4 DUAL-CHAIN OPERATION

  To earn KAS and $zkas from one hash: pull the parent template from a real
  Kaspa node, embed ZKMM||H_zk in its coinbase extra_data, mine it against
  ZKas's bits, and submit the solved parent to BOTH chains — to Kaspa as a
  normal block (earning KAS to your Kaspa address) and to ZKas as an aux block.

  Degrade gracefully: if the Kaspa node is unreachable or still in IBD, fall
  back to a synthetic parent so ZKas blocks keep flowing. That round earns no
  KAS but the ZKas chain stays live.

 6. PAYOUT
-------------------------------------------------------------------------------

 6.1 DIRECT (recommended; what the reference pool runs today)

  Run with no coinbase override. Every block template pays the coinbase to the
  address the finding miner authorized with, and the chain mints it as a
  shielded note to that miner's own zkas: address. The pool never holds miner
  funds, there is nothing to claim, and no signature is ever needed.

  This is by far the simplest correct ZKas pool, and it is a full solo pool.

 6.2 CUSTODIAL

  If you mine to your own treasury address, understand what you are taking on:
  ZKas has NO transparent UTXOs. You cannot sweep with Kaspa payout tooling.
  You need a shielded wallet that can build Orchard transactions.

  Reward discovery is easy: coinbase mints are public on ZKas — recipient and
  value are visible in getShieldedBlocks with no viewing key — so you can watch
  your own treasury's rewards from a plain node stream.

  Paying out is where the cost is. Each shielded transaction can spend at most
  38 notes, and Halo 2 proving costs ~2.4 core-seconds PER NOTE SPENT. A
  treasury that accumulates one coinbase note per block accumulates 86,400
  notes per day. Paying that out one note at a time is hours of CPU.

  The fix is CONSOLIDATION, not more cores: merge many small notes into few
  large ones in the background, so a payout spends 3 notes instead of 300. The
  reference wallet daemon does this automatically.

    zkas-walletd  --auto-consolidate <MAX_NOTES>   (on by default, ceiling 500)
    zkas-walletd  --proof-threads <N>              (cap proving CPU)
    shielded-pay                                    (one-shot CLI send)

  Full playbook, with worked examples for mining pools and exchanges:
    docs/WALLETD.md in the node repo.

  Do NOT set a coinbase override on a live pool until your payout path is
  complete and end-to-end tested. Overriding the coinbase redirects every
  reward to you with no machinery yet to pay it back out.

 7. ERROR MESSAGE -> CAUSE
-------------------------------------------------------------------------------

  "coinbase transaction is not built as expected"
      You rebuilt or rewrote the coinbase and it does not match what consensus
      expects. Almost always the dev-fee output (section 3) or a hardcoded
      payload offset that ignores the 32-byte shielded commitment (section 1, item 3).
      Applies to NATIVE blocks.

  "block has invalid proof-of-work"  (on a merged submission)
      The H_zk you committed into the parent coinbase is not the hash of the
      block you submitted — so the aux binding check failed, and a merged block
      has no native PoW to fall back on. Usually the same root cause as above:
      the coinbase you bound differs from the coinbase you submitted.

  "invalid prefix zkas" / "invalid prefix kaspa"
      Address HRP mismatch between your pay address and the node's network. A
      pre-rebrand node does not know "zkas:"; a Kaspa node never will.

  Aux proof accepted by your bridge but the node says native-only
      Merged mining is gated on that network and the block's DAA score is below
      the activation score. Mine natively until activation.

  Template fetch works, submission always fails, shares look fine
      Check whether you cache and rewrite templates. Section 3.

 9. REFERENCE IMPLEMENTATION
-------------------------------------------------------------------------------

This repo (zkas-pool, a fork of Nacho-the-Kat/katpool) is a working example of
everything above. Useful reading even if you run different software:

    bridge/src/kaspaapi.rs      node RPC: template fetch, submit, merged parent
    bridge/src/merged.rs        AuxPoW assembly and dual-chain submission
    bridge/src/client_handler.rs per-vendor stratum handshakes, job watchdog
    bridge/src/share_handler.rs  share validation and vardiff

Merged mining in the reference bridge is enabled entirely by environment
variables — no code changes:

    ZKAS_MERGED_MINING=1              enable AuxPoW mode
    ZKAS_KASPA_NODE=<host:port>       a real Kaspa node's gRPC
    ZKAS_KASPA_PAY=kaspa:qz9v...      where KAS rewards are paid

Unset ZKAS_KASPA_NODE/PAY (or an unreachable Kaspa node) falls back to a
synthetic parent: ZKas keeps producing blocks, that round earns no KAS.


-------------------------------------------------------------------------------
 10. SUMMARY
-------------------------------------------------------------------------------

  - Mining ZKas is mining Kaspa. Same kHeavyHash, same ASICs, same stratum,
    same difficulty maths. Nothing about the shielded layer touches the miner.
  - Three mandatory changes: accept a non-standard (shielded) coinbase output
    script, never rebuild the coinbase, and account for the extra 32 bytes in
    the coinbase payload.
  - One optional upgrade: merged mining with Kaspa, for KAS and $zkas from one
    hash. Native mining stays valid forever.
  - Pay direct-to-miner unless you have a reason not to. It is simpler, it is
    non-custodial, and it sidesteps shielded payout cost entirely.
  - If you do go custodial, consolidate notes continuously. Proving cost is per
    NOTE, not per coin.
